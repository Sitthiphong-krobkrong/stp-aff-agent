# Plan P3 — Local Review Web App

วางแผนวันที่ 14 พ.ย. 2026 · สถานะ: **มี local Review UI รุ่นแรก; งาน Docker/worker recovery/การทดสอบเบราว์เซอร์ยังค้าง**

## เป้าหมายและขอบเขต

ให้บอทส่งแพ็กเกจคลิปพร้อมหลักฐานและ QA มาที่หน้า Review เพื่อให้คนดู/ฟัง ขอแก้เป็นภาษาธรรมชาติ ดูเวอร์ชันใหม่ แล้วอนุมัติหรือปฏิเสธพร้อมประวัติการตัดสินใจ ไม่มีการโพสต์อัตโนมัติก่อนอนุมัติ ดู [target flow](03_AGENTS_AND_WORKFLOW.md#target-operating-flow--bot-prepares-human-reviews-at-the-end)

เริ่มจากผู้ใช้คนเดียวบน Mac ผ่าน `127.0.0.1` การเปิดให้ใช้จากเครื่องอื่นและ role-based access เป็นงานต่อจากรุ่น local นี้ บอทต้องค้น/ตรวจสินค้าและสิทธิ์สื่อให้ครบก่อนเข้าคิว Review; ถ้าทำไม่ได้ให้รายงาน `BLOCKED` หน้า Review ไม่ทำให้หลักฐานที่ขาดอยู่กลายเป็นหลักฐานที่ผ่านแล้ว ประมาณการ 8–11 วันด้านล่างครอบคลุม **หน้า Review เท่านั้น** ไม่รวมงานทำให้ discovery/rights/QA เป็นอัตโนมัติครบ target flow

## ฐานที่ตรวจพบใน repo

- `agent/pipeline.py` ผลิต `final.mp4`, SRT, `qa_report.json`, `post.txt` และ `manifest.json` ใน `runs/<id>/out/` พร้อมสถานะใน `state.json`
- CLI มี `revise --instruction --avoid-phrase` เพื่อส่งคำแก้ให้ AI และเก็บแพ็กเกจเดิมเป็นเวอร์ชัน, ส่วน `decide approve --reviewed` ตรวจ QA และบันทึก hash ของแพ็กเกจที่อนุมัติ หน้าเว็บควรเรียกกติกาชุดเดียวกันผ่าน service/API
- `READY_FOR_APPROVAL` มาจาก QA ในโค้ด ซึ่งยังยอมรับความเสี่ยงของรูป listing และเตือนเรื่องสิทธิ์เสียง Edge TTS โดยไม่บล็อกเสมอ จึงใช้แทนการตรวจสิทธิ์โดยคนไม่ได้
- มี `agent/review_web.py` เป็น local HTTP server ด้วย Python standard library, `runs/review.sqlite3` เก็บ audit ของคำสั่งจากเว็บ และ `versions/` เก็บผลลัพธ์เดิม ยังไม่มี Dockerfile/Compose หรือ worker ที่ resume งานหลัง process restart

## รูปแบบระบบที่เสนอ

```text
Browser ──> Review API/UI (Docker, 127.0.0.1)
                 ├── SQLite: คำขอแก้ งานในคิว หลักฐานตรวจ และการตัดสินใจ
                 ├── review-data volume: DB และไฟล์หลักฐานสิทธิ์ที่บอทรวบรวม
                 ├── runs/ (read-only mount): MP4, รูป, SRT, QA, post.txt
                 └── HTTP job API <── Mac worker (Python, concurrency=1)
                                       ├── Ollama/Qwen3 หรือ Claude CLI: บทและแผน
                                       ├── LTX-2-mlx: ภาพเคลื่อนไหว (ถ้าเปิดใช้)
                                       └── Edge/Azure TTS + FFmpeg/Pillow: เสียงและ MP4
```

SQLite เป็นแหล่งข้อมูลหลักของ **สถานะ Review**; `state.json` ยังเป็นสถานะ **การผลิต** ของ pipeline แยกกัน Mac worker รับ/รายงานงานผ่าน API จึงไม่ต้องเปิด DB จากสองฝั่ง Docker mount `runs/` แบบอ่านอย่างเดียว ส่วน worker เขียนผลลัพธ์บน Mac และ API แสดงเฉพาะ path ที่ตรวจแล้วว่าอยู่ใต้ `runs/` เท่านั้น ไฟล์หลักฐานที่บอทรวบรวม (หรือคนเพิ่มเพื่อแก้ไข) เก็บใน volume พร้อม hash/path ใน DB และต้องสำรอง volume นี้ CLI `decide` ต้องใช้กติกาการตัดสินใจชุดเดียวกับหน้าเว็บ เพื่อไม่ให้สองช่องทางให้ผลต่างกัน

## เทคโนโลยี

| ส่วน | ใช้ | เหตุผล |
| --- | --- | --- |
| Web/API | Python standard library (`http.server`) ใน local รุ่นแรก; FastAPI + Uvicorn เป็นทางเลือกเมื่อขยาย API | รันได้ทันทีโดยไม่ติดตั้ง dependency เพิ่ม |
| UI | HTML/CSS ที่ server สร้าง | หน้า Review และตัวเล่นวิดีโอในเบราว์เซอร์ |
| ข้อมูล Review | SQLite ผ่าน `sqlite3` | เก็บคำขอแก้ เวอร์ชัน งานคิว และ audit แบบ transaction; ไม่เก็บ MP4 เป็น BLOB |
| Media | ไฟล์ใน `runs/` + path/SHA-256 ใน DB | เก็บไฟล์เดิมและตรวจได้ว่าแต่ละเวอร์ชันใช้อะไร |
| Deployment | Docker Compose เฉพาะ web/API; Mac worker เป็น process บน macOS | LTX/MLX และ Ollama ใช้ GPU/Metal บน Mac |
| งานผลิต | Pipeline, director adapters, TTS, FFmpeg/Pillow เดิม | ใช้เส้นทางผลิตที่มีอยู่และเพิ่มสัญญารับคำแก้ |

## ลำดับงานและประมาณการ

ประมาณการสำหรับผู้พัฒนา 1 คน ทำงานเต็มเวลา โดยมี Docker Desktop และ runtime เดิมพร้อมใช้; เป็นช่วงประมาณ ไม่ใช่วันส่งมอบที่รับประกัน

| ช่วง | งาน | ผลตรวจรับ | เวลา |
| --- | --- | --- | --- |
| 0. สัญญาข้อมูล | กำหนด `run_id`/`version_id`, สถานะ Review, schema คำขอแก้, หลักฐานสิทธิ์ และผลอนุมัติ; ระบุการอ่าน run เก่า | เปิด run เดิมได้โดยไม่แก้ไฟล์เดิม | 0.5–1 วัน |
| 1. ดูงาน | ทำ Docker Compose, API และหน้า list/detail; เล่น MP4, แสดง QA, ซับ, post.txt, รูปและสถานะสิทธิ์ | ดูคลิปจริงและเลื่อนเวลาได้; API อ่านได้เฉพาะไฟล์ใต้ `runs/` | 1.5–2 วัน |
| 2. ตรวจ/ตัดสินใจ | เพิ่ม DB สำหรับหลักฐานและการตัดสินใจ, เช็กไฟล์/สิทธิ์ที่ใช้จริง, บันทึกผู้ตรวจและเหตุผล; รวมกติกากับ CLI | รูป/เสียงที่ไม่มีหลักฐานตามแพลตฟอร์มถูกบล็อก; อนุมัติผิดเวอร์ชันไม่ได้ | 1.5–2 วัน |
| 3. ขอแก้/เวอร์ชัน | ฟอร์มประเภท/เวลา/คำแก้/AI; snapshot ผลเดิม; ส่ง feedback ให้ director; rerun จากขั้นที่เกี่ยวข้อง; คิว Mac worker ทีละงาน | เวอร์ชันเดิมยังเล่นได้; คำแก้มีผลในเวอร์ชันใหม่; งานล้มเหลวตรวจและลองใหม่ได้ | 3–4 วัน |
| 4. ทดสอบและเก็บงาน | ทดสอบ API/DB/worker, เปิดเว็บจริง, ตรวจ responsive/keyboard, ทดสอบ run จริงและ ffprobe หลังแก้ | ผ่านกรณี QA ไม่ผ่าน, สิทธิ์ไม่ครบ, stale version, worker restart และอนุมัติถูกเวอร์ชัน | 1.5–2 วัน |

**รวมประมาณ 8–11 วันทำงาน** โดยหน้าเปิดดูคลิปอย่างเดียวอยู่ช่วงประมาณ **2–3 วันแรก** หากยังต้องแก้สิทธิ์สื่อของสินค้าจริง, credential ของ provider หรือ runtime LTX เวลาส่วนนั้นต้องประเมินเพิ่มจากหลักฐานจริง

## กติกาสำคัญก่อนถือว่าเสร็จ

1. คำขอแก้ต้องผูกกับเวอร์ชันที่คนเห็น บันทึกข้อความตรงตามที่สั่ง พร้อมชนิดการแก้และ AI/model ที่เลือก; คำต้องห้ามที่คนระบุต้องถูกส่งไปยังการสร้างบทครั้งต่อไป
2. ทุกเวอร์ชันเก็บ MP4/SRT/plan/post/QA/manifest และ hash ของผลลัพธ์เดิมไว้แบบไม่ถูกเขียนทับ งานใหม่ต้องผ่าน schema, claim gate, QA และการดู/ฟังโดยคนอีกครั้ง
3. ปุ่มอนุมัติต้องตรวจหลักฐานสิทธิ์สื่อที่ใช้จริงสำหรับ Shopee/TikTok และสิทธิ์เสียงที่เลือก รวมทั้งผลตรวจเนื้อหาโดยคน; `READY_FOR_APPROVAL` อย่างเดียวไม่เพียงพอ
4. งาน AI/render รันพร้อมกันไม่เกินหนึ่งงาน มีสถานะคิว ข้อผิดพลาด และวิธีกลับมาทำต่อหลัง restart; ไม่เรียกงานหนักใน request ของเว็บ
5. หน้าเว็บเปิดเฉพาะ loopback ในรุ่น local, ป้องกันคำขอเปลี่ยนข้อมูลจากเว็บอื่นด้วย token/CSRF, ไม่ให้ URL รับ arbitrary file path, ไม่เก็บ secret ใน DB/log และไม่เพิ่มปุ่มโพสต์อัตโนมัติ

## ขอบเขตที่ยังไม่รวมในรุ่น local

- การเปิดเว็บจากภายนอก, บัญชีหลายคน/role-based control, VPS และการเผยแพร่ผ่าน API: อยู่ใน roadmap ระยะถัดไป
- การพิสูจน์ว่า POC ค้นพบ 3 ผู้สมัครและมีสื่อที่ใช้เชิงพาณิชย์ได้จริง: ต้องมีหลักฐานและทดสอบแยก ไม่ใช่ผลจากการมีหน้า Review
